用 Swift 重寫 DX7 — 和 FM 音源相處的一年

2026年4月23日

起點

只要查過 DX7 的軟體版本，大概都遇過 Dexed 這個 VST 外掛。撐起 Dexed 的引擎是 Raph Levien 在 2012 年寫的 music-synthesizer-for-android（MSFA），一個 C++ 的音源核心。

打開原始碼，大概 2000 行。32 個演算法、包絡線、LFO、回授，全部塞在裡面。密度高得有點不正常。我想把它用 Swift 重寫，跑在 Apple 平台上。

FM 合成，快速版

用一個正弦波去調變另一個正弦波的頻率，就會產生泛音。這就是 FM 的基本原理。DX7 有六個「運算子」，連接方式（演算法）有 32 種。

演算法 1:
OP6 → OP5 → OP4 → OP3 → OP2 → OP1 → out
（六級串聯，OP6 有回授）

演算法 32:
OP6 ─┐
OP5 ─┤
OP4 ─┼→ out
OP3 ─┤
OP2 ─┤
OP1 ─┘
（全載波，接近加法合成）

從 MSFA 學到的事

增益運算在對數域進行

DX7 的 OPS 晶片把所有增益計算都放在對數域做。乘法變成加法，這才讓 1980 年代的硬體跑得動。頻率和增益都是 Q24 定點數的對數表示。不把這個概念裝進腦子裡，後面的程式碼幾乎沒辦法讀。

正弦波查表

1024 個項目的查表，加上線性插值。每個取樣點不會去呼叫 sin()。MSFA 另外準備了一張差分查表，讓你視情況在精度和速度之間取捨。

包絡線不是 ADSR

DX7 的包絡線不是單純的 ADSR。Attack 是非線性的（前半快、後半慢），Decay 是線性衰減。速率值 0 到 99 在內部還會再量化一次。光看規格書，你搞不清楚它實際上是怎麼動的。

32 個演算法只需要六個位元組

每個運算子用一個位元組的旗標表示，整個演算法的路由就是六個運算子乘以一個位元組，共六個位元組。

bits 0-1: output bus (0=main, 1=bus1, 2=bus2)
bit  2:   add flag
bits 4-5: input bus
bits 6-7: feedback

看到這個編碼方式，才真的感受到 1980 年代的工程師把硬體榨到多緊。老實說我滿感動的。

用 Swift 重寫

定點數運算

DX7 跑的是整數運算。Swift 裡我用 Int32 Q24 實作。

// 相位累加器，Q24 格式 — 一個週期 = 2^24
var phase: Int32 = 0
let phaseIncrement: Int32  // freq / sampleRate * (1 << 24)

// 套用增益，先展寬到 Int64 避免溢位
let output = Int32((Int64(sineValue) &* Int64(gain)) >> 24)

這裡有個 Swift 的陷阱。Int32 溢位會直接讓程序崩潰。真的需要讓數值繞回去的地方，得用 &* 或 &+。把 C 的程式碼一行一行照抄，肯定會踩到。

用旋轉矩陣產生正弦查表

// 用旋轉矩陣逐步推進 sin/cos — 累積誤差很小
// [cos(θ+dθ)]   [cos(dθ) -sin(dθ)] [cos(θ)]
// [sin(θ+dθ)] = [sin(dθ)  cos(dθ)] [sin(θ)]

累積誤差小，數值上比較穩定。2048 個項目（數值和差分交錯存放），14 位元線性插值。

exp2 表的問題

把對數轉回線性用的 exp2 表，是 1024 個項目的 Q30 查表加上八度偏移。這裡是 Swift 和 C 在溢位行為上差最多的地方，我重複踩了好幾次。只要一個位元偏掉，增益就會在下游某處差個幾 dB。

包絡線產生器

// Attack：非線性（電平越高，速度越慢）
let step = ((17 << 24 - level) >> 24) &* inc

// Decay / Release：線性衰減
level -= inc

就是那種快速起音、到頂端時慢慢滑進去的 DX7 感覺。光靠規格書寫不出來，我同時開著規格書、MSFA 程式碼、Dexed 的 wiki 和 DX7 服務手冊，來回翻。

音訊執行緒禁止配置記憶體

音訊算圖執行緒不配置記憶體。這點我不妥協。

  • 全部 128 個音色緩衝區在啟動時一次預先配置
  • UI 到音訊的參數傳遞透過無鎖 SPSC 環形佇列進行
  • SynthParamSnapshot 是固定大小的 tuple（用 Array 的話釋放時會觸發堆積操作）
// Array hits the heap
var slots: [SlotSnapshot]

// Tuple is a value type and stays on the stack
var slots: (SlotSnapshot, SlotSnapshot, SlotSnapshot,
            SlotSnapshot, SlotSnapshot, SlotSnapshot,
            SlotSnapshot, SlotSnapshot)

用 Swift 寫即時音訊時，看起來最漂亮的慣用寫法，通常就是那個會出雜音的寫法。

逐位元比對

我把 MSFA 的 C 程式碼編進測試目標，然後用 Int32 逐取樣比對輸出結果。

@Test func voiceOutputMatchesReference() {
    let swiftOutput = swiftVoice.renderBlock(samples: 64)
    let refOutput = dx7ref_voice_render(patch, note, 64)

    for i in 0..<64 {
        #expect(swiftOutput[i] == refOutput[i])
    }
}

這個測試找到了光看波形絕對發現不了的錯誤。用眼睛看，波形永遠「差不多」。但 FM 是非線性的，「差不多」累積下去，音色就完全不同了。

讀取 SysEx 音色

DX7 的音色存在 SysEx（System Exclusive） MIDI 訊息裡。一次 32 個音色的批次傾印是 4104 個位元組。一個音色是 128 個位元組：六個運算子各 17 個位元組，加上 26 個位元組的全域參數。

位元封裝方式毫不留情。Detune 要用 (byte[offset+12] >> 3) & 0x0F 才能取出，還有好幾個欄位共用同一個位元組。原廠 ROM、VRC、DX7II 專用以及 Grey Matter E! 擴充音色包全部都附在裡面。

多音色

真實的 DX7 是單音色，但我也實作了 TX816 風格的多音色模式（TX816 是機架式的兄弟機）。

模式插槽數每插槽音符數
Single116
Dual28
Split28
TX81682

總音符數上限是 16，所以 TX816 模式下是八個音色、每個各兩個音符。

Swift 6 嚴格並行性

整個專案在 Swift 6 嚴格並行性下編譯通過。UI 執行緒和音訊執行緒之間的資料競爭是編譯錯誤，不是執行期才爆的驚喜。

兩種環形緩衝區：

  • SnapshotRing — 用來抓「最新的值」。UI 每次參數變動就推入，音訊執行緒取出最近一筆。
  • SPSCRing — MIDI 事件的 FIFO。Note on/off 的順序有意義，不能丟失任何一筆。

兩者都建在 Synchronization.Atomic 上，使用 acquire/release 順序。沒有互斥鎖，沒有 CAS 迴圈。

最痛的地方

最難熬的是追「音訊稍微跑掉了」這種問題。

波形上看不出來。耳朵聽只覺得「怪怪的」。但逐取樣的 Int32 比對告訴你，exp2 裡的一個位元誤差，透過包絡線放大之後差了好幾 dB，再經過回授路由一遍，就是完全不同的音色。在 FM 這個領域，「基本上正確」撐不過整條訊號鏈。

然後是 Int32 溢位。C 的程式碼依賴那個恰好會繞回去的未定義行為，Swift 就直接崩潰。我把 MSFA 的原始碼從頭到尾翻了一遍，在每個溢位的地方換上 &+ 或 &*。不難，但很長。

收尾

從第一次打開 MSFA，到 M2DX-Core 的 107 個測試全部變綠，大概花了一年。

FM 的原理教科書裡有，但「DX7 的聲音」要靠著追晶片的每一個位元才能得到。這個 Swift 實作站在 Raph Levien（做了 192kHz/24-bit 的真實硬體擷取）和 Pascal Gauthier（Dexed Mark I 引擎）等人的工作之上。
