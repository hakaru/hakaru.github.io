Rewriting the DX7 in Swift — a year with an FM synth

April 23, 2026

Where this started

If you've ever looked into software versions of the DX7, you've run into Dexed, the VST plugin. What actually powers Dexed is music-synthesizer-for-android (MSFA), a C++ engine Raph Levien wrote back in 2012.

Open the source and it's about 2,000 lines. 32 algorithms, envelopes, LFO, feedback — all of it, in there. The density is almost suspicious. I wanted to take that and rewrite it in Swift for Apple platforms.

FM synthesis, fast version

If you modulate the frequency of one sine wave with another sine wave, you get harmonics. That's FM. The DX7 has six "operators" and 32 patterns for wiring them together (the algorithms).

Algorithm 1:
OP6 → OP5 → OP4 → OP3 → OP2 → OP1 → out
(six in series, feedback on OP6)

Algorithm 32:
OP6 ─┐
OP5 ─┤
OP4 ─┼→ out
OP3 ─┤
OP2 ─┤
OP1 ─┘
(all carriers, basically additive)

What MSFA taught me

Gain math happens in the log domain

The DX7's OPS chip does all its gain math in the log domain. Multiplication becomes addition, which is the only reason this ran on 1980s hardware. Both frequency and gain live as Q24 fixed-point log values. Without that in your head, none of the rest of the code makes sense.

Sine wave table

A 1024-entry lookup table with linear interpolation. You don't call sin() per sample. MSFA also keeps a second difference-based table so you can trade accuracy for speed where it matters.

The envelope isn't ADSR

DX7 envelopes aren't a straight ADSR. Attack is nonlinear (fast at first, slow at the end), decay is a linear ramp. Rate values 0–99 get quantized internally on top of that. The spec sheet alone will not tell you how this actually behaves.

32 algorithms fit in six bytes

One byte of bit flags per operator, so the whole routing for one algorithm is six operators × 1 byte = six bytes.

bits 0-1: output bus (0=main, 1=bus1, 2=bus2)
bit  2:   add flag
bits 4-5: input bus
bits 6-7: feedback

Seeing this encoding was the point where I realized how tight the 1980s engineers were squeezing the hardware.

Writing it in Swift

Fixed-point math

The DX7 runs on integer math. In Swift I used Int32 Q24.

// Phase accumulator in Q24 — one cycle = 2^24
var phase: Int32 = 0
let phaseIncrement: Int32  // freq / sampleRate * (1 << 24)

// Apply gain, widen to Int64 to avoid overflow
let output = Int32((Int64(sineValue) &* Int64(gain)) >> 24)

Here's the Swift trap. Int32 overflow crashes the process. When you actually want wrap-around, you have to use &* or &+. Copy the C code line by line and it will definitely crash.

Sine table via a rotation matrix

// Step sin/cos forward with a rotation matrix — small accumulated error
// [cos(θ+dθ)]   [cos(dθ) -sin(dθ)] [cos(θ)]
// [sin(θ+dθ)] = [sin(dθ)  cos(dθ)] [sin(θ)]

Numerically stable because the accumulated error stays small. 2,048 entries (value and delta interleaved), 14-bit linear interpolation.

The exp2 table gotcha

The exp2 table, which takes you from log back to linear, is a 1024-entry Q30 lookup plus an octave shift. This was the main place Swift and C diverge on overflow behavior, and I kept stepping on it. A single bit off at this layer turns into several dB of gain somewhere downstream.

Envelope generator

// Attack: nonlinear (slower as the level gets higher)
let step = ((17 << 24 - level) >> 24) &* inc

// Decay / release: linear
level -= inc

That specific DX7 feel of rising fast and then sliding in at the top. You can't write this from the spec alone — I had the spec, the MSFA code, the Dexed wiki, and a DX7 service manual open at the same time.

No allocation on the audio thread

The audio rendering thread does not allocate. This is the one place I don't compromise.

  • All 128 voice buffers get allocated up front, at startup
  • UI-to-audio parameter handoff goes through a lock-free SPSC ring
  • SynthParamSnapshot is a fixed-size tuple (an Array would dealloc on drop)
// Array hits the heap
var slots: [SlotSnapshot]

// Tuple is a value type and stays on the stack
var slots: (SlotSnapshot, SlotSnapshot, SlotSnapshot,
            SlotSnapshot, SlotSnapshot, SlotSnapshot,
            SlotSnapshot, SlotSnapshot)

When you write realtime audio in Swift, the nice-looking idiomatic version is usually the one that glitches.

Matching bit for bit

I built the MSFA C code into the test target and compared outputs sample by sample as Int32.

@Test func voiceOutputMatchesReference() {
    let swiftOutput = swiftVoice.renderBlock(samples: 64)
    let refOutput = dx7ref_voice_render(patch, note, 64)

    for i in 0..<64 {
        #expect(swiftOutput[i] == refOutput[i])
    }
}

This test found bugs that waveform inspection never would. By eye, waveforms always look "close enough". FM is nonlinear, so "close enough" cascades into a completely different timbre before you notice.

Reading SysEx patches

DX7 patches live in SysEx (System Exclusive) MIDI messages. A 32-voice bulk dump is 4,104 bytes. One voice is 128 bytes: six operators × 17 bytes plus 26 bytes of global parameters.

The bit packing is unsentimental. Detune comes out as (byte[offset+12] >> 3) & 0x0F, and you get multiple fields sharing a single byte. The factory ROM, VRC, DX7II-specific and Grey Matter E! expansion patches are all bundled in.

Multitimbral

A real DX7 is single-timbral, but I also implemented a TX816-style multitimbral mode (the rack-mount sibling).

ModeSlotsVoices per slot
Single116
Dual28
Split28
TX81682

The 16-voice total is a hard cap, so TX816 mode gives you eight patches with two voices each.

Swift 6 strict concurrency

The whole thing compiles under Swift 6 strict concurrency. Data races between the UI and audio threads are a compile error, not a runtime surprise.

Two kinds of ring buffer:

  • SnapshotRing — for "give me the latest value". The UI pushes on every parameter change, the audio thread pulls the most recent one.
  • SPSCRing — FIFO for MIDI events. Note on/off order is meaningful, so nothing gets dropped.

Both are built on Synchronization.Atomic with acquire/release ordering. No mutexes, no CAS loops.

The part that hurt

The worst part was hunting down "the audio is slightly off".

You can't see it in the waveform. You can barely hear it as "something's a bit weird". But sample-by-sample Int32 comparison shows a one-bit error in exp2 turning into several dB through the envelope, and once you route that through feedback you've got a different patch. With FM, "basically correct" does not survive the signal chain.

Then there was Int32 overflow. The C code relies on undefined behavior that happens to wrap around. In Swift it crashes immediately. I went through the MSFA source line by line, swapping in &+ / &* at every overflow site. Not hard, just long.

Wrapping up

From opening MSFA for the first time to getting all 107 of M2DX-Core's tests green was about a year.

The principle of FM is in the textbooks, but "the DX7 sound" requires chasing the actual chip bit by bit. This Swift implementation is sitting on top of the work of Raph Levien (who did 192kHz/24-bit captures of real hardware) and Pascal Gauthier (the Dexed Mark I engine), among others.
