De DX7 herschrijven in Swift — een jaar met een FM-synth

23 april 2026

Hoe het begon

Als je ooit software-versies van de DX7 hebt opgezocht, ben je Dexed tegengekomen — de VST-plugin. Wat Dexed eigenlijk aandrijft is music-synthesizer-for-android (MSFA), een C++-engine die Raph Levien in 2012 heeft geschreven.

Open de broncode en je zit op zo'n 2.000 regels. 32 algoritmen, enveloppen, LFO, feedback — alles erin. De dichtheid is bijna verdacht. Ik wilde dat overnemen en in Swift herschrijven voor Apple-platformen.

FM-synthese, de korte versie

Als je de frequentie van een sinusgolf moduleert met een andere sinusgolf, krijg je boventonen. Dat is FM. De DX7 heeft zes "operators" en 32 patronen om die met elkaar te verbinden (de algoritmen).

Algoritme 1:
OP6 → OP5 → OP4 → OP3 → OP2 → OP1 → out
(zes in serie, feedback op OP6)

Algoritme 32:
OP6 ─┐
OP5 ─┤
OP4 ─┼→ out
OP3 ─┤
OP2 ─┤
OP1 ─┘
(allemaal carriers, eigenlijk additief)

Wat ik van MSFA heb geleerd

Gainberekeningen in het log-domein

De OPS-chip van de DX7 doet al zijn gainberekeningen in het log-domein. Vermenigvuldigen wordt optellen, en dat is de enige reden waarom dit op jaren-tachtig-hardware kon draaien. Zowel frequentie als gain leven als Q24 fixed-point log-waarden. Zonder dat in je achterhoofd begrijp je de rest van de code gewoon niet.

Sinusgolftabel

Een opzoektabel met 1.024 entries en lineaire interpolatie. Je roept geen sin() per sample aan. MSFA houdt ook een tweede op differenties gebaseerde tabel bij, zodat je nauwkeurigheid kunt inruilen voor snelheid waar dat telt.

De envelop is geen ADSR

DX7-enveloppen zijn geen gewone ADSR. De attack is niet-lineair (snel aan het begin, traag aan het einde), de decay is een lineaire helling. Rate-waarden 0–99 worden daar bovenop intern gekwantiseerd. Het spec sheet alleen vertelt je niet hoe dit zich gedraagt.

32 algoritmen passen in zes bytes

Eén byte aan bitflags per operator, dus de volledige routing voor één algoritme is zes operators × 1 byte = zes bytes.

bits 0-1: output bus (0=main, 1=bus1, 2=bus2)
bit  2:   add flag
bits 4-5: input bus
bits 6-7: feedback

Toen ik deze codering zag, drong het pas echt tot me door hoe krap de ingenieurs uit de jaren tachtig de hardware uitknepen.

Het schrijven in Swift

Fixed-point rekenen

De DX7 werkt op integer-rekenen. In Swift heb ik Int32 Q24 gebruikt.

// Fase-accumulator in Q24 — één cyclus = 2^24
var phase: Int32 = 0
let phaseIncrement: Int32  // freq / sampleRate * (1 << 24)

// Gain toepassen, verbreden naar Int64 om overflow te vermijden
let output = Int32((Int64(sineValue) &* Int64(gain)) >> 24)

Dit is de valkuil van Swift. Int32-overflow laat het proces crashen. Als je daadwerkelijk wrap-around wilt, moet je &* of &+ gebruiken. Kopieer de C-code regel voor regel en hij crasht gegarandeerd.

Sinustabel via een rotatiematrix

// Sin/cos vooruitschuiven met een rotatiematrix — kleine geaccumuleerde fout
// [cos(θ+dθ)]   [cos(dθ) -sin(dθ)] [cos(θ)]
// [sin(θ+dθ)] = [sin(dθ)  cos(dθ)] [sin(θ)]

Numeriek stabiel omdat de geaccumuleerde fout klein blijft. 2.048 entries (waarde en delta afgewisseld), 14-bit lineaire interpolatie.

De exp2-tabel: een addertje onder het gras

De exp2-tabel, waarmee je van log terug naar lineair gaat, is een Q30-opzoektabel met 1.024 entries plus een octaafverschuiving. Dit was de voornaamste plek waar Swift en C van elkaar afwijken in overflow-gedrag, en ik bleef er steeds op stappen. Eén bit fout op deze laag leidt stroomafwaarts tot een paar dB gain-verschil.

Envelopgenerator

// Attack: niet-lineair (trager naarmate het niveau hoger wordt)
let step = ((17 << 24 - level) >> 24) &* inc

// Decay / release: lineair
level -= inc

Dat typische DX7-gevoel van snel oplopen en dan zachtjes bovenin aankomen. Dit kun je niet schrijven op basis van de spec alleen — ik had de spec, de MSFA-code, de Dexed-wiki en een DX7-servicehandleiding tegelijk open staan.

Geen allocatie op de audiothread

De audiorendering-thread alloceert niets. Dit is het ene punt waarop ik niet wijk.

  • Alle 128 voice-buffers worden van tevoren gealloceerd, bij het opstarten
  • Parameteroverdracht van UI naar audio gaat via een lock-free SPSC-ring
  • SynthParamSnapshot is een tuple met vaste grootte (een Array zou bij droppen dealloc aanroepen)
// Array raakt de heap
var slots: [SlotSnapshot]

// Tuple is een waardetype en blijft op de stack
var slots: (SlotSnapshot, SlotSnapshot, SlotSnapshot,
            SlotSnapshot, SlotSnapshot, SlotSnapshot,
            SlotSnapshot, SlotSnapshot)

Als je realtime audio in Swift schrijft, is de nette idiomatische versie meestal degene die glitcht.

Valideren tegen de referentie

Ik heb de MSFA C-code in het testdoel gebouwd en de uitvoer sample voor sample vergeleken als Int32.

@Test func voiceOutputMatchesReference() {
    let swiftOutput = swiftVoice.renderBlock(samples: 64)
    let refOutput = dx7ref_voice_render(patch, note, 64)

    for i in 0..<64 {
        #expect(swiftOutput[i] == refOutput[i])
    }
}

Deze test vond bugs die golfvormcontrole nooit zou hebben gevonden. Visueel zien golfvormen er altijd "goed genoeg" uit. FM is niet-lineair, dus "goed genoeg" stapelt zich op tot een volledig ander timbre voordat je het doorhebt.

SysEx-patches lezen

DX7-patches leven in SysEx (System Exclusive) MIDI-berichten. Een bulk dump van 32 voices is 4.104 bytes. Eén voice is 128 bytes: zes operators × 17 bytes plus 26 bytes aan globale parameters.

Het bit-packing is zonder sentiment. Detune kom je eruit als (byte[offset+12] >> 3) & 0x0F, en meerdere velden delen één enkele byte. De fabriks-ROM, VRC, DX7II-specifieke en Grey Matter E! uitbreidingspatches zijn allemaal meegeleverd.

Multitimbraal

Een echte DX7 is single-timbraal, maar ik heb ook een TX816-stijl multitimbrale modus geïmplementeerd (het rack-mount broertje).

ModusSlotsVoices per slot
Single116
Dual28
Split28
TX81682

Het totaal van 16 voices is een harde bovengrens, dus in TX816-modus heb je acht patches met elk twee voices.

Swift 6 strict concurrency

Het geheel compileert onder Swift 6 strict concurrency. Data races tussen de UI- en audiothread zijn een compileerfout, geen verrassing tijdens runtime.

Twee soorten ringbuffer:

  • SnapshotRing — voor "geef me de laatste waarde". De UI pusht bij elke parameterwijziging, de audiothread pakt de meest recente.
  • SPSCRing — FIFO voor MIDI-events. De volgorde van note on/off doet ertoe, dus niets mag verloren gaan.

Beide zijn gebouwd op Synchronization.Atomic met acquire/release-ordening. Geen mutexen, geen CAS-lussen.

Het deel dat pijn deed

Het ergste was het opsporen van "de audio klopt niet helemaal".

Je ziet het niet in de golfvorm. Je hoort het nauwelijks als "er klopt iets niet". Maar sample-voor-sample Int32-vergelijking laat een één-bit-fout in exp2 zien die via de envelop uitgroeit tot een paar dB, en zodra je dat door feedback leidt heb je een ander patch. Met FM overleeft "eigenlijk correct" de signaalweg niet.

Dan was er Int32-overflow. De C-code vertrouwt op undefined behavior dat toevallig wrapt. In Swift crasht het meteen. Ik heb de MSFA-broncode regel voor regel doorgenomen en overal waar overflow kon optreden &+ / &* neergezet. Niet moeilijk, maar saai en lang.

Afronding

Van de eerste keer dat ik MSFA opende tot alle 107 tests van M2DX-Core groen waren, duurde het ongeveer een jaar.

Het principe van FM staat in de leerboeken, maar dicht bij "het DX7-geluid" komen betekende het fixed-point-gedrag van de Dexed/msfa-referentie sample voor sample volgen — niet de werkelijke chip zelf (dit is FM in DX7-stijl, geen cycle-accurate hardware-emulatie). Deze Swift-implementatie staat op het werk van Raph Levien (MSFA, een getrouwe fixed-point FM-engine in DX7-stijl) en Pascal Gauthier (Dexed), onder anderen. Eerlijk gezegd was ik onder de indruk van wat er in die originele broncode zat.
