DX7をSwiftで書き直した — 1年がかりのFM音源移植

2026年4月23日

きっかけ

DX7をソフトで動かす話で必ず出てくるのが Dexed というVSTプラグインで、その中身を支えているのがRaph Levienが2012年に書いた music-synthesizer-for-android（MSFA） というC++のエンジンです。

コードを開いてみると、たった2000行くらいで、32アルゴリズム、エンベロープ、LFO、フィードバックまで全部入っている。異常に密度が高い。これをSwiftで、Apple向けに書き直したい、というのが出発点でした。

FM音源の仕組み、短く

サイン波の周波数を別のサイン波でいじると倍音が出る。これがFMの基本です。DX7は「オペレーター」を6つ持っていて、繋ぎ方（アルゴリズム）が32パターン用意されている。

アルゴリズム1:
OP6 → OP5 → OP4 → OP3 → OP2 → OP1 → 出力
（直列6段、OP6にフィードバックあり）

アルゴリズム32:
OP6 ─┐
OP5 ─┤
OP4 ─┼→ 出力
OP3 ─┤
OP2 ─┤
OP1 ─┘
（全キャリア、加算合成に近い）

MSFAを読んでわかったこと

対数ドメインで掛け算を足し算にする

DX7のOPSチップはゲイン計算を対数領域でやります。掛け算が足し算になるので、80年代のハードウェアでも現実的な速度で動く。周波数もゲインもQ24固定小数点の対数表現。これを頭に入れておかないと、以降のコードはほぼ読めません。

サインテーブル

1024エントリのLUTに線形補間。毎サンプルでsin()は呼びません。MSFAは差分ベースのLUTも別で用意していて、精度と速度を場面ごとに選べるようになっています。

エンベロープがADSRじゃない

単純なADSRではないのがDX7のエンベロープです。アタックは非線形（最初は速くて後半ゆっくり）、ディケイは線形減衰。レート値の0〜99は内部でさらに量子化されている。仕様書だけ読んでも意味がわからないタイプの挙動です。

32アルゴリズムが6バイトで済む

1オペレーターあたり1バイトのビットフラグで、接続を全部表現できます。6オペレーター × 1バイト = 1アルゴリズム6バイト。

ビット0-1: 出力先バス（0=メイン, 1=バス1, 2=バス2）
ビット2:   加算フラグ
ビット4-5: 入力元バス
ビット6-7: フィードバック

この符号化を見たとき、80年代の人たちがどれだけギリギリを攻めていたかがわかって素直に感動しました。

Swiftで書き直す

固定小数点演算

DX7は基本的に整数演算で動きます。SwiftでもInt32のQ24で実装しました。

// 位相アキュムレータ: Q24。1周期 = 2^24
var phase: Int32 = 0
let phaseIncrement: Int32  // freq / sampleRate * (1 << 24)

// ゲイン適用: 64bit中間値でオーバーフロー防止
let output = Int32((Int64(sineValue) &* Int64(gain)) >> 24)

ここでSwiftの罠。Int32はオーバーフローで即クラッシュします。意図的に巻き戻したい場面では &* や &+ を使わないといけない。C版をそのまま写経すると確実にコケるポイントです。

サインテーブルを回転行列で作る

// 回転行列でsin/cosを逐次生成（累積誤差が小さい）
// [cos(θ+dθ)]   [cos(dθ) -sin(dθ)] [cos(θ)]
// [sin(θ+dθ)] = [sin(dθ)  cos(dθ)] [sin(θ)]

累積誤差が小さいので数値的に安定。2048エントリ（値と差分をインターリーブ）、14ビット線形補間で構成しています。

exp2テーブルの罠

対数→線形の変換に使うexp2テーブルは、1024エントリのQ30参照にオクターブ分のシフトを足して作ります。ここでSwiftとCのオーバーフロー挙動の違いを何度も踏みました。1ビットずれるだけで音量が数dB変わります。

エンベロープジェネレータ

// アタック: 非線形（レベルが高いほど遅くなる）
let step = ((17 << 24 - level) >> 24) &* inc

// ディケイ/リリース: 線形減衰
level -= inc

最初速く立ち上がって後半スッと収束する、あのDX7の感じを出すところ。仕様書、MSFAのコード、Dexedのwiki、DX7サービスマニュアル、このへんを行ったり来たりしながらでないと書けませんでした。

オーディオスレッドでのメモリ禁止

オーディオレンダリングスレッドではアロケーション禁止。ここは妥協しません。

  • 128ボイス分のバッファは起動時に一括確保
  • UI→オーディオのパラメータ受け渡しはロックフリーのSPSCリング
  • SynthParamSnapshot は固定サイズのタプルで保持（Arrayはdrop時にdeallocが走ります）
// Arrayはヒープアロケーションが走る
var slots: [SlotSnapshot]

// タプルなら値型でスタックに収まる
var slots: (SlotSnapshot, SlotSnapshot, SlotSnapshot,
            SlotSnapshot, SlotSnapshot, SlotSnapshot,
            SlotSnapshot, SlotSnapshot)

Swiftでリアルタイムオーディオを書くと、一見キレイな書き方で普通にグリッチが出ます。

リファレンスとの照合検証

MSFAのCコードをテストターゲットに組み込んで、サンプル単位でInt32比較しています。

@Test func voiceOutputMatchesReference() {
    let swiftOutput = swiftVoice.renderBlock(samples: 64)
    let refOutput = dx7ref_voice_render(patch, note, 64)

    for i in 0..<64 {
        #expect(swiftOutput[i] == refOutput[i])
    }
}

これをやらないと見つからないバグがたくさん出ました。波形を目で見ても「なんとなく合ってる」になりがちだけど、FMは非線形反応なので「なんとなく」はすぐ音色のズレとして現れます。

SysExパッチの読み込み

DX7のパッチは SysEx（System Exclusive） というMIDIメッセージで保存されます。32音色分のバルクダンプで4104バイト。1音色が128バイトで、6オペレーター×17バイト＋グローバル26バイト。

ビットパッキングが容赦ない。デチューンは (byte[offset+12] >> 3) & 0x0F みたいに1バイト内で複数フィールドが同居しています。ファクトリーROM、VRC、DX7II用、Grey Matter E!拡張パッチまで、代表的なものはバンドルしてあります。

マルチティンバー

DX7の実機は基本1音色ですが、TX816（ラックの兄弟機）風のマルチ動作も実装しました。

モードスロット数1スロットのボイス数
Single116
Dual28
Split28
TX81682

合計16ボイスという制約があるので、TX816モードだと8音色×2ボイスまで、という割り当てです。

Swift 6 Strict Concurrency

全体をSwift 6のStrict Concurrencyでコンパイルしています。UIスレッドとオーディオスレッドのデータ競合はコンパイラが止めてくれる。

リングバッファは2種類。

  • SnapshotRing — 最新値だけ欲しい用途。UIがパラメータ変更のたびに書き込み、オーディオは最新1個だけ取る
  • SPSCRing — MIDIイベント用のFIFO。ノートオン/オフは順序がそのまま意味になるので全部残す

Synchronization.Atomic の acquire/release で組みました。ミューテックスもCASループも使っていません。

きつかった話

一番きつかったのは「音が微妙に違う」の犯人探しでした。

波形の見た目では分からない。聴いても「なんか違う？」くらいのレベル。でもInt32で1サンプル単位で比べていくと、exp2の1ビットズレがエンベロープを通して数dBの差になって、フィードバックを通ると音色が完全に別物になる、という連鎖が見えてきます。FMに関しては「だいたい合ってる」は使えません。

あとはInt32オーバーフロー問題。C側は未定義動作ですが実質ラップアラウンドで動いているコードが、Swiftだと即クラッシュ。MSFAのコードを1行ずつ読んで、オーバーフローしそうなところを &+ / &* に置き換えていく作業を延々とやりました。地味に長い。

おわりに

MSFAのコードを開いてから、M2DX-Coreの107本のテストが全部パスするまで、ざっくり1年でした。

FMの原理は教科書でわかっても、「DX7の音」に近づくには、Dexed/msfaリファレンスの固定小数点の挙動をサンプル単位で追いかける必要がありました——実機チップそのものではありません（これは実機のサイクル精度エミュではなくDX7系FMです）。今回のSwift実装は、Raph Levien（MSFA、DX7系の忠実な固定小数点FMエンジン）やPascal Gauthier（Dexed）らの仕事の上に乗っています。
