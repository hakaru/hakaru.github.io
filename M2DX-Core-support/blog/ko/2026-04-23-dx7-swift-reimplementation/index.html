DX7를 Swift로 다시 쓰다 — FM 신스와 보낸 1년

2026년 4월 23일

시작된 계기

DX7의 소프트웨어 버전을 찾아보면 반드시 만나게 되는 게 Dexed라는 VST 플러그인입니다. 그 안을 실제로 돌리는 엔진이 Raph Levien이 2012년에 만든 music-synthesizer-for-android (MSFA)라는 C++ 코드예요.

소스를 열어보면 약 2,000줄 정도입니다. 32가지 알고리즘, 엔벨로프, LFO, 피드백까지 전부 거기 들어 있어요. 밀도가 이상할 정도로 높습니다. 이걸 Swift로, Apple 플랫폼용으로 다시 써보자는 게 출발점이었습니다.

FM 합성, 짧게 요약

사인파의 주파수를 다른 사인파로 변조하면 배음이 생깁니다. 그게 FM의 기본입니다. DX7에는 "오퍼레이터"가 6개 있고, 연결 방식(알고리즘)이 32패턴 준비되어 있습니다.

알고리즘 1:
OP6 → OP5 → OP4 → OP3 → OP2 → OP1 → out
(직렬 6단, OP6에 피드백 있음)

알고리즘 32:
OP6 ─┐
OP5 ─┤
OP4 ─┼→ out
OP3 ─┤
OP2 ─┤
OP1 ─┘
(전부 캐리어, 가산 합성에 가까움)

MSFA를 읽고 알게 된 것

게인 계산은 로그 도메인에서

DX7의 OPS 칩은 게인 계산을 로그 영역에서 처리합니다. 곱셈이 덧셈으로 바뀌기 때문에 1980년대 하드웨어에서도 현실적인 속도로 돌아갑니다. 주파수와 게인 모두 Q24 고정소수점 로그 표현으로 저장됩니다. 이걸 머릿속에 넣어두지 않으면 이후 코드는 거의 읽히지 않습니다.

사인 파형 테이블

1024개 항목의 LUT에 선형 보간을 씁니다. 샘플마다 sin()을 호출하지 않아요. MSFA는 차분 기반 테이블도 따로 가지고 있어서, 정확도와 속도를 상황에 따라 선택할 수 있게 되어 있습니다.

엔벨로프는 ADSR이 아닙니다

DX7의 엔벨로프는 단순한 ADSR이 아닙니다. 어택은 비선형(처음에는 빠르고 뒤로 갈수록 느려집니다), 디케이는 선형 감쇠. 레이트 값 0~99는 내부에서 또 양자화됩니다. 스펙시트만 읽어서는 실제 동작을 이해할 수 없는 타입입니다.

32가지 알고리즘이 6바이트에 들어가다

오퍼레이터 하나당 1바이트의 비트 플래그로 라우팅을 전부 표현합니다. 6 오퍼레이터 × 1바이트 = 알고리즘 하나가 6바이트.

bits 0-1: output bus (0=main, 1=bus1, 2=bus2)
bit  2:   add flag
bits 4-5: input bus
bits 6-7: feedback

이 인코딩을 봤을 때, 1980년대 엔지니어들이 얼마나 하드웨어를 쥐어짰는지 솔직히 감탄했어요.

Swift로 다시 쓰기

고정소수점 연산

DX7는 기본적으로 정수 연산으로 동작합니다. Swift에서도 Int32의 Q24로 구현했습니다.

// Phase accumulator in Q24 — one cycle = 2^24
var phase: Int32 = 0
let phaseIncrement: Int32  // freq / sampleRate * (1 << 24)

// Apply gain, widen to Int64 to avoid overflow
let output = Int32((Int64(sineValue) &* Int64(gain)) >> 24)

여기서 Swift의 함정이 있습니다. Int32는 오버플로우가 나면 바로 크래시합니다. 의도적으로 래핑이 필요한 곳에서는 &*나 &+를 써야 해요. C 코드를 그대로 옮기면 반드시 터지는 지점입니다.

회전 행렬로 사인 테이블 생성

// Step sin/cos forward with a rotation matrix — small accumulated error
// [cos(θ+dθ)]   [cos(dθ) -sin(dθ)] [cos(θ)]
// [sin(θ+dθ)] = [sin(dθ)  cos(dθ)] [sin(θ)]

누적 오차가 작아서 수치적으로 안정적입니다. 2,048개 항목(값과 차분을 인터리브), 14비트 선형 보간으로 구성합니다.

exp2 테이블의 함정

로그에서 선형으로 변환하는 exp2 테이블은 1024개 항목의 Q30 참조에 옥타브 이동을 더해서 만듭니다. Swift와 C의 오버플로우 동작이 여기서 갈리는데, 여러 번 밟았습니다. 이 레이어에서 1비트만 어긋나도 엔벨로프를 거쳐 수 dB의 게인 차이로 번집니다.

엔벨로프 제너레이터

// Attack: nonlinear (slower as the level gets higher)
let step = ((17 << 24 - level) >> 24) &* inc

// Decay / release: linear
level -= inc

처음에 빠르게 올라가다가 상단에서 스르르 수렴하는, 그 DX7 특유의 느낌을 내는 부분입니다. 스펙시트, MSFA 코드, Dexed 위키, DX7 서비스 매뉴얼을 동시에 열어두고서야 겨우 쓸 수 있었어요.

오디오 스레드에서 메모리 할당 금지

오디오 렌더링 스레드는 할당을 하지 않습니다. 여기서는 타협하지 않습니다.

  • 128보이스 분의 버퍼는 시작 시 일괄 확보
  • UI→오디오 파라미터 전달은 락-프리 SPSC 링을 통해
  • SynthParamSnapshot은 고정 크기 튜플로 보관 (Array는 해제될 때 dealloc이 실행됩니다)
// Array hits the heap
var slots: [SlotSnapshot]

// Tuple is a value type and stays on the stack
var slots: (SlotSnapshot, SlotSnapshot, SlotSnapshot,
            SlotSnapshot, SlotSnapshot, SlotSnapshot,
            SlotSnapshot, SlotSnapshot)

Swift로 리얼타임 오디오를 짜다 보면, 겉보기에 깔끔한 관용구가 글리치를 내는 쪽인 경우가 많습니다.

비트 단위로 맞추기

MSFA C 코드를 테스트 타겟에 내장하고, 샘플 단위로 Int32 비교를 했습니다.

@Test func voiceOutputMatchesReference() {
    let swiftOutput = swiftVoice.renderBlock(samples: 64)
    let refOutput = dx7ref_voice_render(patch, note, 64)

    for i in 0..<64 {
        #expect(swiftOutput[i] == refOutput[i])
    }
}

파형 눈으로 봐서는 못 잡는 버그가 여기서 많이 나왔습니다. 눈으로 보면 항상 "대충 맞는 것 같은데"가 되기 쉽거든요. FM은 비선형이라서 "대충 맞음"이 금방 음색의 차이로 튀어나옵니다.

SysEx 패치 읽기

DX7 패치는 SysEx (System Exclusive) MIDI 메시지에 저장됩니다. 32음색 분의 벌크 덤프가 4,104바이트. 음색 하나가 128바이트로, 6 오퍼레이터 × 17바이트 + 글로벌 파라미터 26바이트입니다.

비트 패킹이 가차 없습니다. 디튠은 (byte[offset+12] >> 3) & 0x0F처럼 1바이트 안에 여러 필드가 공존합니다. 팩토리 ROM, VRC, DX7II 전용, Grey Matter E! 확장 패치까지 대표적인 것들은 번들로 포함시켰습니다.

멀티팀브럴

실제 DX7는 기본적으로 싱글팀브럴이지만, TX816 스타일의 멀티팀브럴 모드도 구현했습니다(랙마운트 형제기입니다).

모드슬롯 수슬롯당 보이스 수
Single116
Dual28
Split28
TX81682

총 16보이스라는 상한이 있어서, TX816 모드에서는 8음색 × 2보이스씩 배분됩니다.

Swift 6 strict concurrency

전체를 Swift 6 Strict Concurrency로 컴파일합니다. UI 스레드와 오디오 스레드 간의 데이터 경합은 런타임 서프라이즈가 아니라 컴파일 에러로 잡힙니다.

링 버퍼는 두 종류입니다.

  • SnapshotRing — "최신 값만 주면 된다"는 용도. UI가 파라미터 변경 때마다 쓰고, 오디오 스레드는 가장 최근 것 하나만 가져갑니다.
  • SPSCRing — MIDI 이벤트용 FIFO. 노트 온/오프 순서 자체가 의미가 있어서 전부 보존합니다.

둘 다 Synchronization.Atomic의 acquire/release 오더링으로 만들었습니다. 뮤텍스도 CAS 루프도 쓰지 않습니다.

힘들었던 부분

가장 고생한 건 "소리가 조금 이상한데"의 원인 찾기였습니다.

파형만 봐서는 모릅니다. 들어봐도 "뭔가 좀 이상한가?" 수준이에요. 그런데 Int32로 샘플 단위 비교를 해보면, exp2의 1비트 오차가 엔벨로프를 거쳐 수 dB 차이가 되고, 피드백을 통과하면 완전히 다른 음색이 됩니다. FM에 관해서는 "대충 맞음"은 안 통합니다.

그리고 Int32 오버플로우 문제. C 코드는 미정의 동작이지만 실질적으로 래핑으로 동작하는 코드가 Swift에서는 즉시 크래시합니다. MSFA 코드를 1줄씩 읽으면서 오버플로우가 날 것 같은 곳을 &+ / &*로 바꿔가는 작업을 쭉 했습니다. 지루하지만 길었습니다.

마무리

MSFA 코드를 처음 연 때부터 M2DX-Core의 테스트 107개가 전부 통과할 때까지 대략 1년이 걸렸습니다.

FM의 원리는 교과서로 이해할 수 있어도, "DX7의 소리"를 내려면 실제 칩의 동작을 비트 단위로 추적해야 한다는 게 체감으로 와닿았습니다. 이 Swift 구현은 Raph Levien(실기 하드웨어의 192kHz/24bit 캡처를 했습니다)과 Pascal Gauthier(Dexed Mark I 엔진) 등의 작업 위에 올라가 있습니다.
