Réécrire le DX7 en Swift — un an avec un synthé FM

23 avril 2026

D'où ça vient

Si vous avez déjà cherché des émulations logicielles du DX7, vous êtes forcément tombé sur Dexed, le plugin VST. Ce qui fait tourner Dexed, c'est music-synthesizer-for-android (MSFA), un moteur C++ que Raph Levien a écrit en 2012.

On ouvre le code source et il y a environ 2 000 lignes. 32 algorithmes, enveloppes, LFO, feedback — tout y est. La densité est presque suspecte. J'ai voulu prendre ça et le réécrire en Swift pour les plateformes Apple.

La synthèse FM, version courte

Si on module la fréquence d'une sinusoïde avec une autre sinusoïde, on génère des harmoniques. C'est la FM. Le DX7 a six « opérateurs » et 32 façons de les câbler ensemble (les algorithmes).

Algorithme 1 :
OP6 → OP5 → OP4 → OP3 → OP2 → OP1 → out
(six en série, feedback sur OP6)

Algorithme 32 :
OP6 ─┐
OP5 ─┤
OP4 ─┼→ out
OP3 ─┤
OP2 ─┤
OP1 ─┘
(tous porteurs, pratiquement de la synthèse additive)

Ce que MSFA m'a appris

Le calcul de gain se fait dans le domaine logarithmique

Le chip OPS du DX7 fait tous ses calculs de gain en domaine logarithmique. La multiplication devient une addition, c'est la seule raison pour laquelle ça tournait sur du matériel des années 1980. Fréquence et gain sont tous les deux stockés en virgule fixe Q24 logarithmique. Sans ça en tête, le reste du code ne tient pas debout.

Table de sinusoïde

Une table de 1 024 entrées avec interpolation linéaire. On n'appelle pas sin() par échantillon. MSFA garde aussi une deuxième table basée sur les différences pour arbitrer entre précision et vitesse selon les besoins.

L'enveloppe n'est pas un ADSR

Les enveloppes du DX7 ne sont pas un ADSR classique. L'attaque est non linéaire (rapide au départ, qui ralentit vers la fin), le decay est une rampe linéaire. Les valeurs de rate de 0 à 99 sont quantifiées en interne par-dessus ça. La fiche technique seule ne vous dira pas comment ça se comporte réellement.

Les 32 algorithmes tiennent en six octets

Un octet de flags par opérateur, donc le routage complet d'un algorithme c'est six opérateurs × 1 octet = six octets.

bits 0-1: output bus (0=main, 1=bus1, 2=bus2)
bit  2:   add flag
bits 4-5: input bus
bits 6-7: feedback

Voir cet encodage, c'est le moment où j'ai compris à quel point les ingénieurs des années 80 serraient le hardware au maximum — honnêtement, ça m'a épaté.

L'écrire en Swift

Arithmétique en virgule fixe

Le DX7 tourne en arithmétique entière. En Swift j'ai utilisé Int32 Q24.

// Accumulateur de phase en Q24 — un cycle = 2^24
var phase: Int32 = 0
let phaseIncrement: Int32  // freq / sampleRate * (1 << 24)

// Appliquer le gain, élargir en Int64 pour éviter le dépassement
let output = Int32((Int64(sineValue) &* Int64(gain)) >> 24)

Le piège Swift, le voilà. Int32 qui déborde fait crasher le processus. Quand on veut vraiment le wrap-around, il faut utiliser &* ou &+. Recopier le code C ligne par ligne, ça crashe à coup sûr.

Table de sinusoïde par matrice de rotation

// Avancer sin/cos avec une matrice de rotation — erreur accumulée faible
// [cos(θ+dθ)]   [cos(dθ) -sin(dθ)] [cos(θ)]
// [sin(θ+dθ)] = [sin(dθ)  cos(dθ)] [sin(θ)]

Numériquement stable parce que l'erreur accumulée reste petite. 2 048 entrées (valeur et delta entrelacés), interpolation linéaire sur 14 bits.

Le piège de la table exp2

La table exp2, qui fait passer du domaine log au domaine linéaire, est une lookup Q30 de 1 024 entrées plus un décalage d'octave. C'est là que Swift et C divergent le plus sur le comportement en cas de dépassement, et j'y suis retombé plusieurs fois. Un seul bit de décalage à ce niveau se transforme en plusieurs dB de gain quelque part en aval.

Générateur d'enveloppe

// Attaque : non linéaire (ralentit à mesure que le niveau monte)
let step = ((17 << 24 - level) >> 24) &* inc

// Decay / release : linéaire
level -= inc

Ce toucher DX7 — montée rapide puis glissement vers le haut. On ne peut pas écrire ça depuis la spec seule. J'avais la spec, le code MSFA, le wiki Dexed et un manuel de service DX7 ouverts en même temps.

Pas d'allocation sur le thread audio

Le thread de rendu audio n'alloue pas. C'est l'endroit où je ne fais aucun compromis.

  • Les 128 buffers de voix sont alloués d'un coup au démarrage
  • La transmission des paramètres UI vers audio passe par un ring SPSC sans verrou
  • SynthParamSnapshot est un tuple de taille fixe (un Array déallouerait à la destruction)
// Array tape dans le tas
var slots: [SlotSnapshot]

// Tuple est un type valeur et reste sur la pile
var slots: (SlotSnapshot, SlotSnapshot, SlotSnapshot,
            SlotSnapshot, SlotSnapshot, SlotSnapshot,
            SlotSnapshot, SlotSnapshot)

Quand on écrit de l'audio temps réel en Swift, la version idiomatique qui a l'air propre est généralement celle qui glitche.

Caler au bit près

J'ai intégré le code C de MSFA dans la cible de test et comparé les sorties échantillon par échantillon en Int32.

@Test func voiceOutputMatchesReference() {
    let swiftOutput = swiftVoice.renderBlock(samples: 64)
    let refOutput = dx7ref_voice_render(patch, note, 64)

    for i in 0..<64 {
        #expect(swiftOutput[i] == refOutput[i])
    }
}

Ce test a trouvé des bugs que l'inspection de forme d'onde n'aurait jamais détectés. À l'œil, les formes d'onde ont toujours l'air « à peu près bonnes ». La FM est non linéaire, donc « à peu près bon » se cascade en un timbre complètement différent avant même qu'on le remarque.

Lire les patches SysEx

Les patches DX7 vivent dans des messages MIDI SysEx (System Exclusive). Un dump en bloc de 32 voix fait 4 104 octets. Une voix fait 128 octets : six opérateurs × 17 octets plus 26 octets de paramètres globaux.

Le packing de bits est sans pitié. Le detune sort comme (byte[offset+12] >> 3) & 0x0F, avec plusieurs champs qui partagent un seul octet. Les patches du ROM usine, VRC, spécifiques au DX7II et les extensions Grey Matter E! sont tous inclus.

Multitimbral

Un vrai DX7 est monotimbral, mais j'ai aussi implémenté un mode multitimbral style TX816 (le grand frère en rack).

ModeSlotsVoix par slot
Single116
Dual28
Split28
TX81682

Le total de 16 voix est un plafond dur, donc le mode TX816 donne huit patches à deux voix chacun.

Swift 6 strict concurrency

Tout ça compile sous Swift 6 strict concurrency. Les data races entre les threads UI et audio sont une erreur de compilation, pas une surprise à l'exécution.

Deux types de ring buffer :

  • SnapshotRing — pour « donne-moi la dernière valeur ». L'UI pousse à chaque changement de paramètre, le thread audio prend le plus récent.
  • SPSCRing — FIFO pour les événements MIDI. L'ordre note on/off a du sens, rien ne doit être perdu.

Les deux sont construits sur Synchronization.Atomic avec ordonnancement acquire/release. Pas de mutex, pas de boucles CAS.

La partie qui a fait mal

Le pire, c'était traquer « l'audio est légèrement faux ».

On ne le voit pas dans la forme d'onde. On l'entend à peine comme « quelque chose cloche ». Mais la comparaison Int32 échantillon par échantillon montre une erreur d'un bit dans exp2 qui se transforme en plusieurs dB à travers l'enveloppe, et une fois routée dans le feedback on obtient un patch complètement différent. Avec la FM, « grosso modo correct » ne survit pas à la chaîne de signal.

Ensuite il y avait le dépassement Int32. Le code C repose sur un comportement indéfini qui se wrap-around par chance. En Swift ça crashe immédiatement. J'ai parcouru le source MSFA ligne par ligne en remplaçant &+ / &* à chaque site de dépassement. Pas dur, juste long.

Pour finir

Entre l'ouverture de MSFA pour la première fois et les 107 tests de M2DX-Core tous au vert, il s'est passé environ un an.

Le principe de la FM est dans les manuels, mais « le son DX7 » demande de traquer le comportement du chip réel bit à bit. Cette implémentation Swift repose sur le travail de Raph Levien (qui a fait des captures 192 kHz/24 bits du vrai hardware) et de Pascal Gauthier (le moteur Dexed Mark I), entre autres.
