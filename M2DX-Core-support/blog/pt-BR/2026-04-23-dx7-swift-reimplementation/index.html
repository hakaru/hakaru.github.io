Reescrevendo o DX7 em Swift — um ano com um sintetizador FM

23 de abril de 2026

Como tudo começou

Se você já pesquisou versões em software do DX7, certamente topou com o Dexed, o plugin VST. O que move o Dexed por baixo é o music-synthesizer-for-android (MSFA), um motor em C++ que Raph Levien escreveu em 2012.

Abre o código e tem umas 2.000 linhas. 32 algoritmos, envelopes, LFO, feedback — tudo ali dentro. A densidade é quase suspeita. Quis pegar isso e reescrever em Swift para plataformas Apple.

Síntese FM, versão curta

Se você modula a frequência de uma onda senoidal com outra onda senoidal, surgem harmônicos. Isso é FM. O DX7 tem seis "operadores" e 32 padrões de conexão entre eles (os algoritmos).

Algoritmo 1:
OP6 → OP5 → OP4 → OP3 → OP2 → OP1 → out
(seis em série, feedback no OP6)

Algoritmo 32:
OP6 ─┐
OP5 ─┤
OP4 ─┼→ out
OP3 ─┤
OP2 ─┤
OP1 ─┘
(todos carriers, basicamente síntese aditiva)

O que o MSFA me ensinou

O cálculo de ganho acontece no domínio logarítmico

O chip OPS do DX7 faz todo o cálculo de ganho no domínio logarítmico. Multiplicação vira adição, e foi só por isso que isso rodava em hardware dos anos 80. Tanto frequência quanto ganho vivem como valores de ponto fixo Q24 em log. Sem isso na cabeça, o resto do código não faz sentido nenhum.

Tabela de seno

Uma tabela de consulta com 1024 entradas e interpolação linear. Você não chama sin() por amostra. O MSFA também mantém uma segunda tabela baseada em diferenças para trocar precisão por velocidade onde faz sentido.

O envelope não é ADSR

Os envelopes do DX7 não são um ADSR simples. O ataque é não linear (rápido no início, devagar no fim), o decay é uma rampa linear. Os valores de rate de 0 a 99 são quantizados internamente em cima disso. Só a folha de especificações não vai te dizer como isso se comporta de verdade.

32 algoritmos cabem em seis bytes

Um byte de flags de bits por operador, então todo o roteamento de um algoritmo é seis operadores × 1 byte = seis bytes.

bits 0-1: output bus (0=main, 1=bus1, 2=bus2)
bit  2:   add flag
bits 4-5: input bus
bits 6-7: feedback

Ver essa codificação foi o momento em que percebi como os engenheiros dos anos 80 estavam espremendo o hardware até o limite. Sinceramente, me impressionou.

Escrevendo em Swift

Aritmética de ponto fixo

O DX7 roda em aritmética inteira. Em Swift usei Int32 Q24.

// Acumulador de fase em Q24 — um ciclo = 2^24
var phase: Int32 = 0
let phaseIncrement: Int32  // freq / sampleRate * (1 << 24)

// Aplica ganho, amplia para Int64 para evitar overflow
let output = Int32((Int64(sineValue) &* Int64(gain)) >> 24)

Aí vem a armadilha do Swift. Overflow em Int32 trava o processo. Quando você realmente quer o wrap-around, tem que usar &* ou &+. Copiar o código C linha por linha vai travar com certeza.

Tabela de seno via matriz de rotação

// Avança sin/cos com uma matriz de rotação — erro acumulado pequeno
// [cos(θ+dθ)]   [cos(dθ) -sin(dθ)] [cos(θ)]
// [sin(θ+dθ)] = [sin(dθ)  cos(dθ)] [sin(θ)]

Numericamente estável porque o erro acumulado fica pequeno. 2.048 entradas (valor e delta intercalados), interpolação linear de 14 bits.

O problema da tabela exp2

A tabela exp2, que leva de log de volta para linear, é uma consulta Q30 de 1024 entradas mais um shift de oitava. Foi aqui que Swift e C mais divergiram no comportamento de overflow, e fiquei tropeçando nisso várias vezes. Um único bit errado nessa camada vira alguns dB de ganho lá na frente.

Gerador de envelope

// Ataque: não linear (mais devagar conforme o nível sobe)
let step = ((17 << 24 - level) >> 24) &* inc

// Decay / release: linear
level -= inc

Aquela sensação específica do DX7 de subir rápido e depois deslizar suavemente no topo. Não dá pra escrever isso só com a spec — eu tinha a spec, o código do MSFA, a wiki do Dexed e o manual de serviço do DX7 abertos ao mesmo tempo.

Sem alocação na thread de áudio

A thread de renderização de áudio não aloca. Esse é o ponto onde não abro mão.

  • Todos os 128 buffers de voz são alocados de uma vez, na inicialização
  • A passagem de parâmetros da UI para o áudio vai por um ring lock-free SPSC
  • SynthParamSnapshot é uma tupla de tamanho fixo (um Array dealoca ao ser descartado)
// Array vai para o heap
var slots: [SlotSnapshot]

// Tupla é um value type e fica na stack
var slots: (SlotSnapshot, SlotSnapshot, SlotSnapshot,
            SlotSnapshot, SlotSnapshot, SlotSnapshot,
            SlotSnapshot, SlotSnapshot)

Quando você escreve áudio em tempo real em Swift, a versão que parece mais idiomática geralmente é a que causa glitch.

Validação em relação à referência

Compilei o código C do MSFA no target de testes e comparei as saídas amostra por amostra como Int32.

@Test func voiceOutputMatchesReference() {
    let swiftOutput = swiftVoice.renderBlock(samples: 64)
    let refOutput = dx7ref_voice_render(patch, note, 64)

    for i in 0..<64 {
        #expect(swiftOutput[i] == refOutput[i])
    }
}

Esse teste encontrou bugs que a inspeção visual de formas de onda jamais encontraria. Visualmente, as formas de onda sempre parecem "perto o suficiente". FM é não linear, então "perto o suficiente" vira um timbre completamente diferente antes de você perceber.

Lendo patches SysEx

Os patches do DX7 vivem em mensagens MIDI SysEx (System Exclusive). Um bulk dump de 32 vozes tem 4.104 bytes. Uma voz ocupa 128 bytes: seis operadores × 17 bytes mais 26 bytes de parâmetros globais.

O empacotamento de bits não tem dó. Detune sai como (byte[offset+12] >> 3) & 0x0F, e vários campos dividem um único byte. Os patches da ROM de fábrica, VRC, específicos do DX7II e da expansão Grey Matter E! estão todos incluídos.

Multitimbral

Um DX7 de verdade é single-timbral, mas também implementei um modo multitimbral no estilo TX816 (o irmão em rack).

ModoSlotsVozes por slot
Single116
Dual28
Split28
TX81682

O total de 16 vozes é um limite fixo, então o modo TX816 te dá oito patches com duas vozes cada.

Swift 6 strict concurrency

O projeto inteiro compila com Swift 6 strict concurrency. Data races entre as threads de UI e áudio são um erro de compilação, não uma surpresa em runtime.

Dois tipos de ring buffer:

  • SnapshotRing — para "me dá o valor mais recente". A UI empurra a cada mudança de parâmetro, a thread de áudio puxa o mais recente.
  • SPSCRing — FIFO para eventos MIDI. A ordem de note on/off tem significado, então nada se perde.

Os dois são construídos sobre Synchronization.Atomic com ordenação acquire/release. Sem mutexes, sem loops CAS.

A parte que doeu

O pior foi caçar o "o áudio está levemente errado".

Você não consegue ver na forma de onda. Mal dá pra ouvir como "tem algo estranhinho". Mas a comparação Int32 amostra por amostra mostra um erro de um bit no exp2 virando alguns dB através do envelope, e quando você roteia isso pelo feedback tem um patch completamente diferente. Com FM, "basicamente correto" não sobrevive à cadeia de sinal.

Aí tinha o overflow de Int32. O código C depende de comportamento indefinido que por acaso faz wrap-around. Em Swift trava na hora. Fui pelo código-fonte do MSFA linha por linha, trocando &+ / &* em cada ponto de overflow. Não é difícil, só é chato e longo.

Conclusão

De abrir o MSFA pela primeira vez até todos os 107 testes do M2DX-Core ficarem verdes foi mais ou menos um ano.

O princípio do FM está nos livros, mas chegar perto do "som do DX7" significou seguir o comportamento de ponto fixo da referência Dexed/msfa amostra a amostra — não o chip real em si (isto é FM no estilo DX7, não uma emulação de hardware com precisão de ciclo). Essa implementação em Swift está sobre o trabalho de Raph Levien (MSFA, um motor FM fiel de ponto fixo no estilo DX7) e de Pascal Gauthier (Dexed), entre outros.
